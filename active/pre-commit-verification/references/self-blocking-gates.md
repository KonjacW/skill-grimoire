# 自设守门的两个反向假信号

守门脚本（「核对一致才允许删/才允许报完成」这类）本身会给出错误信号，且**两个方向都会出错**。
真实踩坑记录（2026-09-17，删除前核对）：

## 1. 假红：判定式类型不匹配 ⇒ 该过的时候不过

```python
miss = [f for f in src_files if f not in dst_set]      # 列表
bad  = [f for f in ... if h(a) != h(b)]                # 列表
ok = (miss == 0) and (bad == 0) and (n == n2)          # ✗ [] == 0 恒为 False
```

后果：打印明明是 `缺失=0 不一致=0`，判定却是 FAIL —— **假红**，会白白中止一次正确操作
（本例中止了删除，损失为零，但若守门用在「必须继续」的路径上就是卡死）。

**规则：守门判定一律写 `len(x) == 0`，不写 `x == 0`。**

## 2. 假绿：守门只覆盖了「宽」的一侧

同一守门如果只查「目标缺文件」（`src 有 dst 没有`），就会漏掉「内容被改」；
只查抽样又会漏掉单文件漂移。本例修好判定式后才发现：改动方是**守门自己人** ——
被核对的清单文件在归档之后又被追加了一节（+780 字节），于是造成一处真实差异。

**规则：核对要全量逐文件哈希（不是抽样），且两个方向都查（缺失 + 内容不同）。**

## 3. 守门必须自证分辨力（两个方向都要证）

只证明「不一致时它会红」不够，还要证明**「一致时它会绿」**：

* 造一个确定一致的输入 ⇒ 守门必须返回通过（否则是假红）；
* 造一处确定不一致的输入 ⇒ 守门必须返回失败（否则是假绿）。

代价极低（改一个字节即可），而跳过它就可能出现上面两种错误。

## 4. 附属坑：时间戳的时区

`execute_code` 的 kernel 走 **UTC**，本机可能是本地时区 ⇒ 它打印的 `mtime` 与
资源管理器/`terminal` 看到的**差一个时区偏移**（本例 UTC+8 差 8 小时，14:30 实为 22:30）。
排查「谁改了这个文件」时若拿错时间戳，会归因到不存在的「外部进程」。
⇒ 用户可见的时间戳从 `terminal` 的 `date` 取，或显式换算。
