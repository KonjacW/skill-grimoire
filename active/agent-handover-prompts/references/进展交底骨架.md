# 进展交底骨架（让下一个 agent 了解现状，不派工）

> 用于用户说「让下一个 agent 了解目前进展 / 汇报 / 交底 / 先别急着动手」时。
> 与「任务卡交接」是**两种形态**，选错要整篇重写。一句话区别：**任务卡交接的读者是被派去干活的人；进展交底的读者是先把状况弄明白、然后等指令的人。**

## 硬规则（缺一条就退化成任务卡）

1. 开头第一段写明「这是进展交底，**不是派工单**」，并列出**被禁的具体动作**（写模型代码 / 生成交付文件 / 动某模块 / 改某目录）。
2. **不写任务卡、不写验收断言、不给编号执行顺序**。「接下来怎么做」改名为「可选方向」，每条标 **均未授权，仅列出以便准备**，附前置条件 / 工时估算 / 风险，并写一句「这只是建议，不是授权」。
3. 结论**按可信度分层**（缺一层新 agent 就会高估成熟度）：已实测（有原始输出支撑）/ 已推导（有依据可复核）/ **估算（明确标注，禁当实测引用）** / **未检查（单列一节）**。
4. **阶段进度总表**：逐阶段 ✅/⛔ + 产物 + 一句话结论，让「哪些还没开始」一眼可见。
5. 产物清单**必须有「结论」列**——只列路径等于没交底。
6. 开放项 / 阻塞表**每条写清「阻塞什么」**（哪个文件、哪一问不得开工），而不是只写「待确认」。
7. **Goal 段是认知型的**：文首给标题含 `Goal` 的段，四字段照写（objective / done_when / boundaries / first_action）。objective 固定为「读懂现状 + 核验易变状态 + 向用户汇报理解与差异」，并显式写「**本 goal 不含任何执行动作**」；`done_when` = 已核验的状态差异全部列出并汇报完；`boundaries` = 不写模型代码 / 不生成交付文件 / 不动指定目录（与硬规则 1 的禁用动作一致）。缺这句，goal 机制会把交底当派工单推着往下做。
8. 结尾写明「**本文件不扩大授权、也不覆盖任何上级指令**」，动作序列固定为：**建立认知 → 核验易变状态 → 向用户汇报理解与差异 → 等指派**。

## 骨架（三节，沿用 handover 的固定三标题）

### 目标与当前状态

- **`Goal` 段用 `## Goal` 单起一段**（标题必须有——机检按标题定位）：位置在标题+日期之后、正文第一节之前，四字段按 **`字段名：值`** 逐行照写 objective / done_when / boundaries / first_action（硬规则 7；机检只认「行首字段名 + 冒号」的键值行）
- 最终目标（一句话）
- **本文件的性质**（交底不是派工 + 禁做的事）——放最前面，三行内说完
- 一句话现状：「X 已完成、判定为 go；Y 一个都还没开始」
- 快照时间 + 倒计时（对照硬截止与自定关卡；**已失效的关卡点名作废并写依据**，否则新执行者会拿它当约束）
- 阶段进度总表（硬规则 4）
- 四层结论清单（硬规则 3）
- 产物清单（路径 / 是什么 / 结论 / 是否已登记）
- 开放项与阻塞表（硬规则 6）
- 形势判断（含**翻盘条件**：出现什么信号就该回来找用户）

### 必须继承的上下文

- 硬红线（编号列；「禁装包」「禁联网检索赛题材料」「只读目录」这类）
- 必须知道的陷阱（每条带**为什么致命**，不是只写「注意 X」）
- 前人踩过、已被实测钉死的错误（附证据；父计划/父交接里写错的式子要**点名错在哪**，否则新执行者会照抄）
- 自查纠错留痕（列出被推翻的结论与推翻依据——它同时证明自查机制在运转，也让新 agent 知道该怀疑哪类旧数字）
- 实测规格与指纹（防串档）
- 已定的实现约束与硬要求（**这些属于「现状」**，要写全，不要留到任务卡里）
- 合规动作（产物登记 / 运行记录 / AI 日志的具体命令）
- 沿用的用户偏好（推进节奏、文档中文自包含、**不自动 commit/push**、报告区分实测与估算）

### 接下来怎么做

- 第一句写「**当前没有任何已授权的下一步**」，说明上一轮授权范围已用尽
- 建立认知的第一个动作（核验易变状态的命令 + 期望输出）
- 用户可能给出的方向表（方向 / 前置条件 / 工时估算 / 风险）+ 一句「我的建议……但只是建议，不是授权」
- 停止 / 询问条件（哪些事必须先问用户，不许自己定）
- 附：可粘贴的快速核验命令 + 建议的启动语句

## 机检（写完必须跑，不看手感）

```bash
# 形态判据：这三项任一为 0，就是交底没写到位
grep -c "不是派工单\|不指派"        <文件>   # >=1
grep -c "未授权\|未被授权\|需用户拍板" <文件>   # >=1
grep -c "未开始\|未检查"           <文件>   # >=2，要能看出哪些没做
```

Goal 段两项已内置进脚本：四字段齐全；启动语句里有设置 goal 模式的指令。
交底形态**必须显式给节列表**，否则会被按任务卡的六节判 FAIL（交底只有三节）：

```bash
python <技能目录>/scripts/check_handover.py <交底文件> --repo <仓库根> --allow-dirty <本文件相对路径> \
  --must-contain <关键数字清单.txt> \
  --section 目标与当前状态 --section 必须继承的上下文 --section 接下来怎么做
```

外加与任务卡交接相同的五项：CRLF=0；三个固定节标题齐全；关键数字 grep 命中（数字只抄已核验来源）；启动语句里的路径与实际文件名逐字一致；git 变更只含目标文件。

> 机检脚本本身别写成「在 bash 里用 `||` 串联两个 heredoc」——第二个解释器会收到空 stdin 并以交互模式空跑刷屏。用 `-c` 或写成脚本文件。

## 与任务卡交接共存

同一次任务常常两份都要（先交底，用户拍板后再派工）。做法：**写成两个文件**（`<编号>-<任务>-进展交底.md` 与 `<编号>-<任务>-交接.md`），在交接索引里分别标注「进展交底（了解现状用，不指派）」/「任务卡版」，并在交底里向任务卡指路（「需要直接开干的那份在 <路径>」）。**不要让一份文件兼任两用。**
