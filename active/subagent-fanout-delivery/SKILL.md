# 子代理 fan-out 交付（多产物批量并行）

用于：一次任务要产出多个同类文件/模块（检查器套件、批量文档、多目录改造、批量生成器）；也用于**只读勘察/取证类**并行调查（见《只读取证类 fan-out》，其并行判据与产出类不同）。**不适用**：单文件小改（直接干）；需要用户拍板方向的子任务（不派子代理）。

## 铁律

1. **共享契约先落盘**：统一状态枚举 / 数据结构 / 报告格式写成共享模块（`core.py` 之类），主 agent 先写完并冒烟通过，子代理只 `import`、禁止修改。口头规范会被各自重新发明——落盘契约不会。
2. **产物唯一路径**：任务卡写明每个子代理产物的**全路径** + 统一结构 + 「禁止修改他人文件」；同目录并行时各写独立文件即无冲突。
3. **小批多次**：一批 2-4 个子代理、每个 3-4 个产物；一次 10 个并行的协调/审查成本与失败面成倍上升。批间由主 agent 汇总验收后再开下一批。
4. **任务卡自包含**：子代理看不到主对话——背景、路径、依赖现状（哪些库已装）、验收命令、输出结构全部写进 context；只给 goal 会得到风格分裂的产物。已有落盘计划文件时，任务卡改为「先读 `<plan 路径>` 的 §X 小节并严格执行」+ 关键约束摘要——比复制全文更省、且不会与计划漂移；但路径、验收命令、依赖现状仍必须写全。
5. **自测必须走真命令行**：只直调函数的 `--smoke` 会掩盖参数解析层缺陷（实战：子命令 `dest="cmd"` 与 `--cmd` 子参数冲突 → 真命令行恒打帮助 rc=2，而函数直调自测全绿）。每个产物的自测至少含一条真 CLI 路径。
6. **自报不可信**：子代理「已完成 / smoke 通过」只是自报。主 agent 必须亲自跑：`py_compile` 全部产物 → 逐个自测 → 关键复现用例，才算验收。**写作类产物同理**：子代理自称「数字全部来自源文件」不等于取对了，主 agent 必须抽样回源 grep 核验（见铁律 11）。
7. **部分失败直接补齐**：个别子代理因外部原因（provider 计费 402、超时）失败时，主 agent 直接写缺失产物、核实同批其余文件是否完整落盘，不整体重派；外部阻断用一句话报给用户（充值 / 换 provider 属用户侧动作）。
8. **状态语义集中**：多态结论（通过 / 阻断 / 高风险 / 人工确认 / 未检查）用共享枚举；「有阻断→不可发布」「未检查不得转通过」写进共享模块的单一门槛函数，各模块只填事实、不各自解释。
9. **给 agent 用的工具集必须带 agent 入口**：人用 CLI 手册不算交付。配薄封装（场景名→底层 CLI 映射，单行 JSON：`{ok, exit_code, conclusion, reports, stdout}`）+ `AGENTS.md` 场景路由表 + `--list`；生成类场景（输出里没有「结论：」行）要回退用输出末行当结论，否则 agent 侧解析为空。
10. **平台造不出的用例抽纯函数**：非法文件名/保留名（Windows 下 `:` 会变 NTFS 数据流、CON/NUL 为保留名）无法用样本文件构造——文件根本不出现在遍历里，用例假绿。把判定抽成纯函数（如 `filename_illegal(name)`）直接断言；样本文件只测能真实存在的形态。
11. **同一工作区常并存「原型期/计划期」与「交付期正式」两套参数，子代理会取错**：从既有项目里抽事实写文档时，「正式网格/正式参数」类数字极易抓到早期的原型值。核验时不能只问「这个数字在源文件里出现过吗」，要问**「这个数字属于哪个阶段」**——查每个数值旁的阶段限定词（规划期/原型/drift/收口后/最终）。实测捕获两类：把原型网格 `dr=0.025 cm (N=80)` 当成正式求解网格（正式为 `dr=0.00078125 cm, N=2560`），把原型期的迭代次数/残差当作最终值。**任务卡里让子代理给每个关键数字标注「值 + 阶段 + 出处文件」**，比只要求「不许编造」有效得多。

12. **负对照与「跑一遍」类验证要先分因，别只看退出码**：产物脚本的路径多由自身位置推导（如 `next(p for p in HERE.parents if (p/'01_赛题').is_dir())`），把复制副件放到仓库外会让它在判定前就崩——**崩溃与判定翻转同为 rc=1**，于是假「有判别力」。负对照副本放仓库内（`.gitignore` 覆盖的临时目录），把完整输出存文件后核「是不是真打印了 FAIL / 真的是那一项为 false」；grep 只筛关键词会把 traceback 静默滤掉而看起来「无输出」。

13. **并行子代理若要各自起本地服务/实例，端口与清理口径必须在任务卡里成对写死，并禁止按进程名扫杀**：给每个子代理分配互不相同的端口（静态服务口 / CDP 口 / 调试口全部错开）并在卡片里给出「你的口是 X、Y」；收尾口径写死「只按端口抓 PID 清你自己的（`netstat -ano | grep -E ':<你的口>'` + `taskkill /PID <p> /T /F`），**不要**按进程名或别人的 PID 扫杀」，同时写「只清自己起的实例，用户自己的应用进程（如 `Hermes.exe`）绝不碰」。实战：两路子代理各自起 dev 实例做 CDP 验证，其中一路收尾时顺手把「疑似残留的 npx wrapper」清掉，实际杀的是另一路正在用的 vite —— 对方实例当场倒掉、白跑一轮，还额外消耗一轮纠偏。隔离只做「静态端口不同」不够，清理口径也必须各自封闭。

## 每批收尾（固定动作）

```bash
python -m py_compile <本批全部文件>                      # 语法
for f in <本批模块>; do python "$f.py" --smoke; echo "$f exit=$?"; done   # 自测
```
主 agent 复核通过后再把产物登记进项目索引/状态文件（未登记视为未检查），然后开下一批。

## 长文 / 多章节文档的 fan-out（写作类）

多章节长文的合并成本几乎全在「可拼接性」和「风格一致」这两点上，都要在任务卡层面预先钉死（任务卡自包含、产物唯一路径仍按铁律 2/4）：

- **主代理先定骨架，章节标题逐字写进任务卡**：全篇一级标题编号 + 每章 2-4 个二级标题由主代理定好，子代理只写自己那几节。让子代理自拟标题，合并时必出现编号断档、层级重复、同一概念各写一套译名。
- **片段而非文档**：要求纯 Markdown 片段——**不要 YAML frontmatter、不要文档总标题**，层级直接用 `#`（章）与 `##`（节），N 份草稿才能顺序拼成一篇。
- **风格块原样复贴到每份任务卡**：读者定位、术语首次出现要一句解释、二级标题下先 1-3 句判断、3 个以上对象用表格、Mermaid 节点写法、公式与引用块约定——写成一段固定文字逐份复制。写「按统一风格」等于没写，风格必然分裂。
- **草稿写在工作区外的临时目录**（`$LOCALAPPDATA/Temp/<task>-draft/`）：受管工作区（有「未登记视为未检查」登记表、Git 仓库、提交/评审门禁的）不接受派生产物，直接写进去会污染资源索引与提交面。子代理只从工作区**读**素材，最终文件由主代理核验后落到目标位置。
- **每份草稿末尾用 HTML 注释登记取材**（`<!-- 取材：<路径1>；<路径2> -->`）：合并时删掉，但它是回源核验的唯一线索。
- **写作类子代理必配反编造约束**：任务卡列全源文件的绝对路径清单，并写死「所有数字、结论、文件名、路径必须来自这份清单，没读到的不许写；不要写『一般认为』『通常情况下』」。写作类最常见的失败不是漏写，而是补出听起来合理的通用说法。
- **用 output_schema 让子代理回交 `file_path / headings / 字数 / 关键事实+来源文件`**，主代理据此抽几条数字回源文件核一遍——比通读全文核验便宜一个量级。

## 只读取证类 fan-out（搜索 / 清点 / 比对 / 审计 / 记录检索）

调查型任务（扫 rollout、清点会话库、比对两个副本、审计仓库）与产出类的并行门禁不同：**≥3 个可独立推进的只读工作包 + 各自写不同产物文件 + 写权互不相交**即默认分片并行，**无须论证收益大于成本**（零写冲突，集成成本仅为汇总）。判据见 `using-superpowers`《一次并行判断》B 档。派发要点：

- **任务卡必写项**（自包含要求同铁律 4）：① 自包含背景——调查范围、编号/计数口径、已知边界、要核验的假设全部写进 context；② 每个工作包产物的**唯一全路径**；③ 只读禁令——不得修改/创建/删除被查对象、不得 git 写操作（需要子代理写 findings 时，显式声明「只写指定的 findings 文件」为唯一例外）；④ **禁启动长任务**——禁止仿真、全量 pytest、任何长命令或本地服务，只允许 `read_file` / `search_files` / 轻量 grep（同机器有长批次在跑时，这条不写必污染 wall-clock）；⑤ 限步收尾——「读完就回答，N 个工具调用内收尾」；⑥ `output_schema` 回交——至少含 `file_path / 结论 / 关键数字 + 出处`。
- **批处理可能被中途杀死**：并行批次会被外部原因中断（主 agent 收尾、宿主判 stalled 并终结、资源抢占），所以任务卡写死「**先落盘报告骨架**（首行 `status: 进行中`），每完成一项即更新该文件」。否则被杀时手里零落盘，前面读的全白费；有骨架时最少也能拿到部分取证结果。
- **主 agent 必须亲自复算关键数字**：汇总数字是子代理自己算术的产物，重复计入、路径形态不同都不会自曝。实测两例：① **跨来源相加重复计入**——两个 glob 各自匹配到同一批 rollout（一个按目录、一个按索引），相加得 254，按唯一键去重后实为 **227**；② **同一对象两种路径形态被当成两个对象**——rollout 索引里写相对路径 `r0/active/<name>/SKILL.md`，CLI 打印绝对路径，只看一种形态会把「索引在场」统计错（漏计或重复计）。复算前先把两侧归一成同一基准（`realpath` / `basename`），并在任务卡里写明「按什么键去重」。
- 汇总时以主 agent 复算值为准；与子代理报数不一致的，在报告里写明差异来源（重复计入 / 路径形态 / 口径不同）。

## 审查类 fan-out（只读子代理做独立 Review）

独立 Review 是「信息隔离」型委派：子代理看不到主对话，价值就在于不共享主 agent 的假设。要点：

- **范围清单派发前用 `git status` / `git diff --stat` 实测生成**（基线 commit、已提交范围、已暂存、
  未暂存、涉及路径），不要凭记忆列。漏列会让审查者把步数花在「你少给了文件」上，而且它会
  独立重判风险等级（任务卡里自填的风险等级对它不具约束力）。
- **任务卡写死只读 + 资源禁令**：禁止修改/提交/推送/再委派；若同机器上正在跑长批次，额外写死
  「只允许 `read_file` / `search_files` / 轻量 grep，禁止启动仿真、全量 pytest 或任何长命令」——
  否则审查者的重活会污染同批 wall-clock 计时并打爆内存。
- **限步收尾**：任务卡末尾直接写「读完就回答，N 个工具调用内收尾，不要无限拓展范围」。审查类
  任务天然倾向越读越多，不加限度的批次会很久不返回。
- **用 `output_schema` 统一返回**：findings 数组每条要求 severity / file_line / behavior 必填，
  另加 blocking 布尔（以及需要它单独判的项，如“某处判据修正是否合理”）。主 agent 才能机械地
  处置 P1/P2，而不是再通读一遍长文。
- **批次返回后先确认结果真的回来了再往下走**：拿到交付失败或空结果时，把范围再收窄后重派一次，
  不要把 push / 交付门禁挂在一次可能未返回的长批次上；也不要因为一次投递失败就改用自审——
  自审不算独立门禁，宁可把门禁未满足如实报给用户。

## 返工与修复

- 验证批发现的问题列「问题清单」，**修复集中由主 agent 或一个修复子代理执行**（子代理只记录、不擅改他人文件），修完必须跑原自测 + 原复现用例回归。验证样例按类留档（每类一子目录），复现命令与退出码写进问题清单，修复者照着跑即可回归。
- 已知限制（无法自动判定）应输出「人工确认」而非通过或阻断——把「不能判」和「判错了」严格分开。

## 交付形态三处一致

统一入口（薄封装）/ `AGENTS.md` 场景路由 / 人工手册，三处必须同步更新，否则下一个会话会按旧入口调用。
